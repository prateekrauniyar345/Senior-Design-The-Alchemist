\section*{Executive Summary}
\addcontentsline{toc}{section}{Executive Summary}

\noindent The Alchemist is a full-stack software system that allows users to query, explore, and visualize mineral data from Mindat.org through natural-language interaction rather than manual API construction. The project addresses a clear usability gap: although Mindat exposes rich geological data, the underlying query parameters and response structures create a barrier for students, researchers, and non-specialist users who need evidence quickly but do not know the data model in advance.

\noindent The final solution combines a React frontend, a FastAPI backend, Supabase-based authentication, a LangGraph supervisor, specialized collection and visualization agents, and an MCP server that exposes Mindat-oriented tools to the agent workflow. Users can request mineral datasets, locality data, and chart-oriented outputs such as histograms, heatmaps, scatter plots, and map-like visual summaries. The design adds value through three key choices: pre-LLM validation that blocks malicious or unsupported requests before tool execution, specialization of agent responsibilities to reduce routing ambiguity, and persistence of chat sessions so outputs remain traceable and reusable.

\noindent From both technical and business perspectives, the system improves access to open mineral data, reduces query-format errors, supports repeatable analysis, and offers a deployment path based on widely used cloud services. Repository evidence and poster validation indicate that representative histogram, heatmap, and network-style prompts were exercised; invalid hardness filters were constrained to the Mohs 0--10 domain; malicious or prompt-injection style inputs were blocked before agent execution; and general greetings were routed to a conversational agent instead of being rejected. The result is a practical design that turns an expert-oriented data portal into a safer and more approachable analytical interface.

\section{Background}
Mindat.org is an important open mineral data source, but practical access to that data still assumes that users understand API endpoints, filter names, and response structures \citep{mindat}. The project poster describes this gap directly: open mineral data are available, but exploring them can be difficult for users who are not already comfortable with parameterized requests and raw JSON responses. In that environment, a conversational interface is not simply a convenience feature; it is a translation layer between the language of domain questions and the language of an expert-oriented data portal.

The Alchemist was motivated by the opportunity to reduce that gap with an LLM-assisted software layer that can interpret user intent, retrieve the appropriate mineral or locality dataset, and return results in a form that is easier to inspect. The repository shows that the final system supports mineral filtering, locality lookup, generated chart specifications, persistent chat sessions, and cloud deployment documentation. Those capabilities make the system relevant to several stakeholder groups: geology students who need faster exploratory analysis, researchers who want a lightweight way to prototype queries, project sponsors who need an accessible demonstration of LLM utility in a scientific data context, and future maintainers who need a modular architecture that can be extended without rewriting the full stack.

The benefit proposition is therefore both technical and organizational. Technically, the system reduces the number of manual steps between a user question and a usable data set or visualization. Organizationally, it demonstrates a reproducible pattern for applying LLM agents to open-data portals while retaining safety checks, service boundaries, and deployment documentation. That combination is the central opportunity pursued by the project.

\section{Problem Definition}

The primary goal of The Alchemist is to provide a user-friendly, deployable, and safer interface for querying Mindat mineral data in natural language. In practical terms, the project had to deliver more than a chatbot. It needed a structured workflow that could distinguish between conversational questions, mineral-data requests, locality-data requests, and visualization requests; guard the system against unsupported or malicious prompts; and return outputs that users could inspect or reuse.

The project deliverables reflected that goal:

\begin{itemize}
    \item React-based chat interface for authenticated interaction,
    \item FastAPI backend that exposes application routes and stores user sessions,
    \item LangGraph-based supervisor that routes requests to specialized agents,
    \item Mindat-oriented tool endpoints exposed through an MCP server,
    \item Visualization support for chart or plot outputs,
    \item Deployment guidance for Vercel (frontend) and Render (backend plus MCP service),
    \item Validation and testing evidence for supported and unsupported requests.
\end{itemize}

\section{Concepts Considered}

\section{Concept 1: Direct Query Forms over the Mindat API}

The most straightforward concept was a conventional web application with fixed search forms mapped directly to Mindat query parameters. In this design, users would choose filters such as hardness range, crystal system, or country from a structured interface, and the application would submit conventional REST requests without an LLM in the middle. This concept offered clear advantages: it would be deterministic, easier to test than an agentic system, and less expensive to operate because it would not require a model call for every user interaction.

However, the approach does not solve the full problem that motivated the project. Mindat exposes many possible query combinations, and building a complete form-driven interface would either overwhelm the user with options or require the team to limit the problem to a small subset of the data portal. It also provides little help when the user's request combines multiple intents, such as ``show IMA-approved minerals containing iron and then visualize the returned hardness distribution.'' A direct-form concept is feasible, but it is fundamentally less expressive than the problem statement required.

\section{Concept 2: Single-Agent LLM with Direct API Calls}

A second feasible concept was a monolithic LLM agent responsible for everything: interpreting the prompt, selecting parameters, calling the Mindat API, and deciding how to visualize the result. This design would have reduced implementation complexity in the short term because only one agent prompt and one orchestration path would need to be maintained. It also aligned with common prototype patterns in which an LLM is given tool access and allowed to reason end to end.

The weakness of this concept is control. A single-agent design is harder to debug, harder to constrain, and more likely to mix unrelated responsibilities in the same reasoning chain. If it misinterprets a prompt, the failure can be difficult to localize. It also makes prompt-injection or tool-misuse risks more consequential because the same reasoning loop handles both interpretation and action. For a classroom prototype, this concept could work; for a reportable engineering design, it does not provide enough separation of concerns.

\section{Concept 3: Multi-Agent Workflow with Internal Tool Calls}

The third concept introduced specialization: separate agents would handle general conversation, mineral data collection, locality collection, and visualization planning. This structure improves observability because routing decisions become explicit, and tool responsibilities are tied to narrower prompts. The repository's workflow and sequence diagrams show that this idea survived into the final architecture.

Even within a multi-agent concept, the team still had alternatives for tool integration. One option was to expose Python functions directly within the backend process and allow the agents to call them as ordinary tools. This would have been sufficient for a tightly scoped demo and would eliminate the need for an additional service. The downside is that it mixes tool execution, API orchestration, and user-facing backend logic in a single runtime. That makes independent deployment and future reuse harder.

\section{Concept 4: Multi-Agent Workflow with MCP Tool Isolation}

The selected concept extends the multi-agent idea with a more disciplined service boundary. In the final design, Mindat-related tools are exposed through a FastMCP server, and the LangGraph agents load those tools through an MCP client layer. This has two advantages that matter in a design report. First, it keeps the backend's user-facing responsibilities distinct from the tool-serving responsibilities. Second, it creates a cleaner pattern for future extension, because additional domain tools can be added to the MCP service without rewriting the entire frontend or routing stack.

The MCP-based concept also aligns well with the problem's educational value. It demonstrates not only that an LLM can query data, but that modern agent systems benefit from explicit tool boundaries and structured orchestration. That makes the project more defensible as a software-engineering artifact than a prompt-engineering demo.

\section{Visualization Alternatives}

Visualization required its own concept exploration. The repository still contains traces of earlier plotting directions such as static histogram, network, and heatmap generation through Python plotting libraries. These approaches remain valid for export-oriented deliverables, and the codebase includes utilities and service hooks for plot handling, download, and email delivery. Static rendering is attractive because it is deterministic and familiar.

The final design moved toward LLM-generated Vega-Lite specifications for a broader class of charts. That choice increases flexibility. Instead of writing custom plotting code for every new request pattern, the system profiles returned data and generates a chart grammar that the frontend can render interactively. The tradeoff is that chart correctness now depends partly on the LLM's ability to choose meaningful encodings, which is why profile-based chart planning and validation prompts became important architectural supports.

\section{Security and Usability Alternatives}

Another design choice concerned how early to reject bad inputs. A permissive concept would send almost every prompt into the agent workflow and rely on the general agent or tool errors to recover gracefully. The final implementation rejects that idea. The validation layer runs before the graph workflow and explicitly handles empty prompts, overlong inputs, off-topic requests, malicious instructions, and invalid domain parameters. That decision improves both safety and user experience because blocked requests are intercepted before tool execution, while still returning brief, redirected explanations.

\section{Summary of Viable Concepts}

The concept study did not identify impossible paths; rather, it showed that some feasible paths were better aligned with the project's learning goals and stakeholder needs than others. The direct-form concept was too restrictive, the monolithic agent concept was too opaque, and the internal-only multi-agent concept was less modular than desired. The selected architecture balanced flexibility, safety, extensibility, and demonstrability better than the alternatives.

\section{System Architecture}

\subsection{Architecture Overview}

The Alchemist uses a three-tier software architecture augmented by an external tool service. The user interacts with a React frontend \citep{react}. That frontend communicates with a FastAPI backend \citep{fastapi} that handles authentication-aware routing, persistence, validation, and orchestration. The backend in turn invokes a LangGraph workflow \citep{langgraph} whose agents access Mindat-oriented functions through an MCP server powered by FastMCP \citep{fastmcp}. The architecture is shown in Figure~\ref{fig:architecture}.

\begin{figure}[H]
\centering
\includegraphics[width=0.6\textwidth]{architecture.png}
\caption{High-level system architecture of The Alchemist}
\label{fig:architecture}
\end{figure}

This architecture is conceptually strong because each layer has a defensible responsibility. The frontend owns interaction and rendering. The backend owns application rules, session state, and API surface. The LangGraph layer owns task decomposition and agent sequencing. The MCP server owns domain tool exposure. The Mindat API remains the authoritative source of mineral and locality data. That separation reduces coupling and gives the project a clearer maintenance path than a single-process prompt-driven prototype.

\subsection{Frontend Layer}

The frontend is implemented in React with Vite, React Router, Axios, and Vega/Vega-Lite dependencies \citep{react,vegalite}. The chat page manages conversation state, saved sessions, and authentication-aware navigation. Returned assistant messages can include plain text, sample data, or chart specifications, and the UI maps those payloads into renderable message objects. This supports a more analytical workflow than a standard chat interface because responses can carry structure, not only prose.

The user-experience design adds practical value in two ways. First, conversations persist by session, which makes the tool usable for iterative exploration rather than one-off demos. Second, the chart rendering path allows the same interface to display both textual interpretations and chart payloads without forcing the user into a separate analysis tool.

\subsection{Backend Application Layer}

The FastAPI application aggregates multiple routers, including default health routes, authentication routes, user and profile routes, session routes, Mindat routes, agent routes, and plot routes \citep{fastapi}. The backend also mounts a contents directory so that generated data and plots can be served back to the frontend. In production, CORS is configured to allow the deployed Vercel frontend to communicate with the backend using credentialed requests.

From a systems perspective, the backend does more than expose endpoints. It is the policy layer of the application. It decides when a user is authenticated, which session a message belongs to, how validation failures are communicated, and how structured outputs are stored and returned. This is important because LLM-enabled products fail when application logic is allowed to dissolve into prompt text. The Alchemist avoids that error by keeping validation, routing, and persistence in explicit Python code.

\subsection{Validation Layer}

One of the most meaningful design improvements in the final system is the pre-LLM validation layer. Before the backend sends a prompt into the agent graph, it checks for empty input, insufficiently meaningful content, length violations, malicious or unsafe content, off-topic requests, and parameter-level issues such as invalid hardness ranges. Inputs longer than 500 characters are rejected, and hardness constraints are mapped to the domain-valid 0--10 Mohs range.

This layer is especially important because the project interacts with live tools. Without validation, unsupported or hostile requests would still consume model calls and create noisy failure cases. By placing validation ahead of the LLM workflow, the system reduces risk and clarifies user expectations. Recent improvements also use the LLM to rewrite validation feedback into concise user-facing redirections without allowing the blocked input itself to drive tool use.

\subsection{Agent Workflow}

The orchestration layer is implemented as a LangGraph state machine with a supervisor node, four specialized agent nodes, and a finish node \citep{langchain,langgraph}. The supervisor does not answer user questions directly. Instead, it selects the next agent among the general conversational agent, geomaterial collector, locality collector, Vega visualization generator, or workflow completion. The routing logic is governed by an explicit system prompt and a structured output schema rather than open-ended narrative reasoning.

\begin{figure}[H]
\centering
\includegraphics[width=0.88\textwidth]{workflow.png}
\caption{Agent workflow used by the LangGraph supervisor}
\label{fig:workflow}
\end{figure}

The graph structure supports a disciplined three-step pattern for visualization tasks: collect the relevant dataset, generate a chart specification once sample data are available, and then finish. Pure data requests terminate earlier. General greetings and capability questions route to the general agent. This sequencing is shown conceptually in Figure~\ref{fig:workflow} and at the message-exchange level in Figure~\ref{fig:sequence}.

\end{figure}

\subsection{MCP Tool Layer}

The MCP service is implemented with FastMCP and exposes at least three domain tools: geomaterial collection, locality collection, and sample-data profiling \citep{fastmcp}. The collector tools convert natural-language-derived parameters into strongly shaped Mindat queries, call the upstream API, and save returned results as JSON files in the backend contents directory. The profile tool then analyzes the returned dataset structure without loading the entire raw dataset into the LLM context.

\begin{figure}[H]
\centering
\includegraphics[width=0.92\textwidth]{mcp.png}
\caption{MCP service role in tool mediation}
\label{fig:mcp}
\end{figure}

This is one of the project's most novel features. Instead of treating tool use as an implementation detail hidden inside a single process, the system makes tool mediation visible and extensible. That improves modularity and creates a reusable pattern for future scientific-data agents.

\section{Testing Procedures}

Testing combined code-level checks with prompt-driven workflow evaluation. At the prompt level, the repository includes a curated set of representative histogram, heatmap, and network-style requests that can be reused for regression testing. The poster further indicates that the team tested multiple prompt categories to ensure that the system could distinguish between geomaterial, locality, conversational, and unsafe inputs. These tests are appropriate for an LLM-based interface because correctness depends not only on unit behavior, but on the interaction between classification, routing, tools, and rendering.

At the backend level, the application structure supports targeted testing of router logic, validation behavior, and response composition. At the frontend level, the project includes a Vite build pipeline and explicit deployment instructions for environment-variable configuration. Together, these make it possible to verify that the integrated system still builds and deploys after code changes.

The recommended test procedure for final submission is:
\begin{enumerate}[leftmargin=0.75in]
    \item run backend import or compile checks on validation, router, and agent modules;
    \item run the frontend production build;
    \item execute a representative positive prompt suite across mineral, locality, and chart requests;
    \item execute negative prompts for malicious requests, off-topic requests, empty input, and invalid hardness ranges;
    \item verify that session persistence and authenticated routing still work after multi-message use.
\end{enumerate}

\section{Observed Results}

The strongest evidenced results available in the repository and poster are qualitative but still meaningful:
\begin{itemize}[leftmargin=0.75in]
    \item representative visualization-oriented prompts were exercised across histogram, heatmap, and network categories;
    \item hardness filters were constrained to valid Mohs-scale inputs rather than naively interpreting unrelated numeric phrases;
    \item malicious or system-prompt-style requests were blocked before agent execution;

\section{Sustainability Assessment}

From a sustainability perspective, The Alchemist is relatively efficient for a modern full-stack AI prototype. It leverages an existing open-data source rather than duplicating a proprietary data collection pipeline. It uses common open-source frameworks with large support communities, which reduces maintenance friction. It can also operate on free-tier services during development, limiting infrastructure waste while the design is still changing.

The main sustainability tradeoff is that LLM-backed services incur recurring operational cost and external dependency risk. The architecture partially mitigates this by separating concerns and allowing future optimization steps such as request caching, evaluation-guided prompt tuning, or fallback modes when the model or upstream data service is unavailable. In short, the system is sustainable as a research and educational platform, but production-scale use would require more deliberate cost and reliability engineering.

\section{Future Work}

The Alchemist is beyond the idea stage, but it is not yet the end state of the product. The most important recommendation for the sponsor is to treat the current system as a validated architecture rather than a finished production platform. Its next phase should focus on measurement, reliability, and task coverage.

First, the team should build an automated evaluation harness around the existing prompt suite. A two- to three-week effort could convert the current manual prompt bank into a repeatable regression system that scores routing correctness, blocked-input behavior, and chart-generation success. This would provide the quantitative evidence still missing from the current report draft.

Second, the team should improve operational visibility. Two to four additional weeks would be sufficient to add richer tracing dashboards, service-level alerts, and failure logging around the backend, MCP service, and upstream Mindat calls. This work is especially important if the sponsor intends to demonstrate the system repeatedly or hand it off to another student team.

Third, several features remain promising but incomplete or only partially realized:
\begin{itemize}[leftmargin=0.75in]
    \item broader chart comparison workflows and richer network visualizations,
    \item improved export paths for chart specifications and cleaned datasets,
    \item caching of common Mindat requests to reduce latency and model cost,
    \item stronger fallback behavior when external services are degraded,
    \item expanded domain prompts beyond the currently supported mineral and locality patterns.
\end{itemize}

In cost terms, the immediate next step remains modest. A practical cloud baseline is approximately \$14 per month for two starter Render services, plus whatever Azure OpenAI and other API usage charges are incurred. A focused 4--8 week continuation effort by a small student team or sponsor-backed developer would be sufficient to convert the current prototype into a more rigorously measured pilot system.
